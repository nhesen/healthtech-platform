# DigiSolution Hackathon Deployment

This runbook deploys the architecture already in this repository:

| Component | Runs where | Connects to | Main environment variable |
|---|---|---|---|
| Patient app | Physical phone / Expo Go | Public FastAPI | `EXPO_PUBLIC_API_URL` |
| Doctor/Admin | Vercel or laptop browser | Public FastAPI | `NEXT_PUBLIC_API_URL` |
| Backend | Render | Supabase PostgreSQL | `DATABASE_URL` |
| CV | Presentation laptop | Public FastAPI | `CV_BACKEND_URL` |

The mobile app is not deployed to Vercel. Vercel is only for the Next.js Doctor/Admin interface. All records included in the hackathon seed are synthetic.

## 1. Supabase PostgreSQL

Create an empty Supabase project and copy its PostgreSQL connection string. Prefer the Supabase pooler/session URL when the backend host is IPv4-only and include `sslmode=require`. The backend connects directly through `DATABASE_URL`; the repository does not use browser-side Supabase Auth or public Storage credentials.

From the repository root, verify a clean database and install the schema without manual SQL:

```powershell
$env:PYTHONPATH="backend"
$env:DATABASE_URL="postgresql://...?...sslmode=require"
.\.venv-win\Scripts\python.exe -m app.migrate
.\.venv-win\Scripts\python.exe -m app.seed
```

`app.migrate` is idempotent. `app.seed` explicitly restores the deterministic synthetic dataset. Normal backend restarts do not duplicate seed records because the seed version is recorded in `demo_seed_versions`.

## 2. Render backend

Create a Render Blueprint from the repository root using `render.yaml`. Configure these secret or deployment-specific values in Render:

- `DATABASE_URL`: Supabase PostgreSQL connection string
- `CORS_ORIGINS`: exact Vercel production URL, plus trusted local URLs if required, comma-separated
- `AI_API_KEY`: optional; leave empty while `AI_PROVIDER=mock`
- `AI_PROVIDER`: `openai` only when the key is configured, otherwise `mock`
- `CV_SERVICE_TOKEN`: generated by Render; copy it securely to the presentation laptop

The service uses the repository's actual commands:

```text
Build: Dockerfile in backend/
Pre-deploy: python -m app.migrate
Start: python -m app.migrate && python -m uvicorn app.main:app --host 0.0.0.0 --port $PORT
Health: GET /health
```

The Render disk at `/data` stores private uploaded files. The database remains Supabase PostgreSQL; do not add a second PostgreSQL service. After deployment:

```powershell
$backendUrl="https://healthtech-api.onrender.com"
Invoke-RestMethod "$backendUrl/health"
$env:DEMO_BACKEND_URL=$backendUrl
.\.venv-win\Scripts\python.exe backend\scripts\demo_check.py
```

Expected health fields are `status=ok`, `database=connected`, and `demo_mode=true`.

## 3. Vercel Doctor/Admin web

Import this repository into Vercel and set the project root directory to `frontend`. Configure:

```text
NEXT_PUBLIC_API_URL=https://healthtech-api.onrender.com
NEXT_PUBLIC_DEMO_MODE=true
```

Update backend `CORS_ORIGINS` to the exact Vercel production origin, then redeploy the backend. Next.js owns `/doctor/*` and `/admin/*`, so direct navigation and refresh do not need SPA rewrites.

CLI alternative, from `frontend`:

```powershell
npm ci
npm run build
npx vercel --prod
```

## 4. Expo Patient on a physical phone

Copy the safe example and set the real public HTTPS backend:

```powershell
Copy-Item apps\patient-mobile\.env.example apps\patient-mobile\.env
cd apps\patient-mobile
npm ci
npx expo start --lan
```

Scan the QR code with Expo Go. All current dependencies are Expo Go-compatible. If Metro has stale state:

```powershell
npx expo start --clear --lan
```

`EXPO_PUBLIC_API_URL` must be the Render HTTPS URL, without a trailing slash. Never put the database password, Supabase service-role key, AI key, or CV token in an `EXPO_PUBLIC_*` variable.

Optional internal Android APK after Expo Go succeeds:

```powershell
cd apps\patient-mobile
npx eas-cli login
npx eas-cli build --platform android --profile preview
```

The first EAS run links the project to the owner's Expo account. EAS is optional and does not block the Expo Go demo.

## 6. Demo reset

Reset is available only when `DEMO_MODE=true`. It returns `404` when disabled.

```powershell
$backendUrl="http://localhost:8000"
Invoke-RestMethod -Method Post -Uri "$backendUrl/demo/reset" -Headers @{"X-Demo-User"="admin@demo.az"}
```

For the deployed hackathon service, replace `$backendUrl` with the Render HTTPS URL. Do not enable demo mode for a future real-data environment.

## 7. CV on the presentation laptop

Install the lightweight simulator dependencies with the backend requirements already installed. Set the public URL and the same token stored in Render:

```powershell
$env:PYTHONPATH="cv_service"
$env:CV_BACKEND_URL="https://healthtech-api.onrender.com"
$env:CV_SERVICE_TOKEN="..."
.\.venv-win\Scripts\python.exe cv_service\run_demo.py --simulate
```

Prepared-video mode needs the optional vision packages:

```powershell
.\.venv-win\Scripts\python.exe -m pip install -r cv_service\requirements-vision.txt
$env:PYTHONPATH="cv_service"
$env:CV_BACKEND_URL="https://healthtech-api.onrender.com"
$env:CV_SERVICE_TOKEN="..."
$env:CV_MODEL="yolo11n-pose.pt"
$env:CV_VIDEO_PATH="C:\path\to\fall_risk_demo.mp4"
.\.venv-win\Scripts\python.exe cv_service\run_demo.py --video $env:CV_VIDEO_PATH
```

The recommended hackathon topology is local prepared video/simulator → public HTTPS backend → Admin Safety page. Cloud GPU/video deployment is deliberately not required.

## 8. AI and fallback

Live AI secrets belong only on Render:

```text
AI_PROVIDER=openai
AI_API_KEY=<server secret>
AI_MODEL=gpt-4o-mini
AI_BASE_URL=https://api.openai.com/v1
```

Set `AI_PROVIDER=mock` or remove `AI_API_KEY` to exercise the deterministic fallback. AI does not control clinical access, consent, appointment state, insurance math, discharge state, or safety events.

## 9. Hackathon startup and pre-flight

1. Verify Render `GET /health` reports a connected database.
2. Run `python backend\scripts\demo_check.py` against the deployed URL.
3. Reset the demo once from the web panel or `/demo/reset`.
4. Open the Vercel Doctor and Admin routes in the laptop browser.
5. Start Expo, scan the QR code, log in, and load Health on the physical phone.
6. Book Dr. Leyla, verify `60 / 48 / 12 AZN`, grant consent, and confirm it appears in Doctor web.
7. Run the local CV simulator and verify Room 204 changes to `HIGH FALL RISK` in Admin.
8. Complete the Patient #104 discharge/cleaning flow and verify capacity changes.
9. Reset again, reopen mobile/web, and repeat the critical path.

Do not claim physical-device or public-cloud verification until steps 1–9 have been performed using the real deployed URLs. Hosting accounts, Supabase credentials, and the physical handset are external prerequisites and are not stored in this repository.
